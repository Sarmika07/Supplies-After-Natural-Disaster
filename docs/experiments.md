# Experimental protocol and results

## Objective

Measure whether ReliefRoute can recover a last-minute disaster-relief delivery plan faster than a simple dispatcher-style repair while making the service, cost, emissions and reliability trade-offs visible.

## Baseline

The baseline is deliberately simple and reproducible:

1. Apply the same disruption to the same snapshot.
2. Sort released work by priority, then deadline.
3. Find feasible vehicles using hard capacity, fuel-reserve and shift constraints.
4. Append each stop to the nearest feasible route.
5. Never reconsider an earlier insertion.

A separate operational reference point is an **8-minute manual rebuild target** for the small four-route scenario. This is a scenario assumption, not a claim about every relief organisation.

## ReliefRoute planner

ReliefRoute uses the same constraints but searches insertion positions across all available vehicles and ranks candidates using:

- service: 40%
- cost: 15%
- distance: 15%
- emissions: 10%
- reliability: 15%
- stability: 5%

Completed stops are immutable. Capacity, fuel reserve and driver shift limits are hard constraints. Infeasible work is explicitly escalated.

## Recovery-time definition

`elapsedMs` measures wall-clock runtime of the deterministic planner function from disruption state to a complete proposed plan. It is **solver recovery time**, not field driving time. The operational comparison is against the 480-second manual rebuild assumption.

## Failure matrix

| Case | Disruption | Expected behaviour |
|---|---|---|
| Vehicle breakdown | V-07 unavailable | Reassign pending work without using V-07 |
| Urgent addition | New S-15, 420 kg Critical | Insert new work while preserving earlier commitments |
| Cancellation | S-07 cancelled | Remove the commitment without touching completed work |
| Road closure | A12 closed | Recover affected stops and account for detour |
| Capacity shortage | V-12 loses 1,200 kg | Reassign overflow while treating capacity as hard |
| Infeasible overload | Only 300 kg reserve vehicle remains | Escalate impossible demand instead of pretending it is served |

## Measured benchmark

The checked-in benchmark artifact is generated by `pnpm experiment` and contains both planner comparison and the manual recovery reference.

| Case | ReliefRoute runtime | Manual reference | Service | Protected commitments | Unassigned |
|---|---:|---:|---:|---:|---:|
| Vehicle breakdown | 2.4 ms | 480 s | 100% | 100% | 0 |
| Urgent addition | 1.1 ms | 480 s | 100% | 100% | 0 |
| Cancellation | 0.1 ms | 480 s | 100% | 100% | 0 |
| Road closure | 0.7 ms | 480 s | 100% | 100% | 0 |
| Capacity shortage | 0.5 ms | 480 s | 100% | 100% | 0 |
| Infeasible overload | 0.1 ms | 480 s | 33.3% | 100% | 10 |

The exact millisecond values can vary slightly by CPU; the experiment checks the target as `<2 seconds`, not as an exact timing claim.

## Trade-off interpretation

- **Vehicle breakdown:** ReliefRoute reduced distance by about 1.0%, cost by 1.6% and emissions by 1.7% versus the simple baseline while using fewer route changes.
- **Road closure / capacity shortage:** the adaptive planner accepted a small distance/cost/emissions increase in the recorded snapshot because it protected route stability and retained all deliverable service. This is intentional: the system is not distance-only optimisation.
- **Infeasible overload:** both planners expose 10 unassigned stops. This is a successful safety behaviour because the hard constraints make full recovery impossible; the system escalates instead of inventing a feasible plan.

## Error analysis

The main error state is infeasibility. When no vehicle satisfies capacity, fuel reserve and shift constraints, the stop is placed in `unassignedStops` and a decision-trace message explains the escalation. This makes failure observable to a dispatcher and testable in automated runs.
